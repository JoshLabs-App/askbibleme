## 已作废

### 划重点灵敏度修复（2026-09-13）
- **决定**：修复划重点 pan 手势漏字问题，不删除功能。
- **为什么**：根因是 `paintAt` 每次只标当前触点的 1 个字符，手指快划时两次回调之间的字符被跳过。基础设施（TextKit 绘制、存储、会员同步、HighlightBar UI）已全齐，修复成本低（约 20 行），删除浪费。
- **修法（最终 Fix 5）**：去掉 pan gesture，改用 `FlowTextView.touchesBegan/Moved/Ended` 直接接触摸。`prevPaintIdx` 填补连续区间；`pendingPaints`+`liveHighlightRuns` 在手势结束前仅在本地绘制预览，结束时批量提交 `onPaint`（消除每字符 SwiftUI 刷新的卡顿）；`setParentScrollEnabled` 同时设 `delaysContentTouches = false`，阻止 ScrollView 抢触摸。
- **验证**：2026-09-13 安装真机验收通过，丝滑连续。
- **日期**：2026-09-13

### 划重点两个 bug 修复（2026-09-13 真机复验通过）

**Bug 1：黄色落不下来（persistence 断链）**
- **根因**：加节号高亮支持时把 `textStarts = built.textRanges` 改成了 `built.ranges`（含节号），导致 `paintAt` 里算出的字符下标与 `VerseHighlightStore` 存储格式错位，`runs()` 找不到对应区间，`highlightRuns` 始终为空。
- **修法**：`textStarts = built.textRanges`，`textOffsets = [:]`，回到 Fix 5 坐标映射。节号视觉高亮靠 `runs()` 里 `runStart == 0 → fullStart` 的扩展逻辑处理，不需要在 `paintAt` 里覆盖节号区。
- **日期**：2026-09-13

**Bug 2：下部分选不了（touch blocking）**
- **根因**：`ParchmentCardModifier` 的 background 内部有一张 `UIScreen.main.bounds.height` 高的羊皮纸图，该背景视图会截获 SwiftUI 触点，使底部 ~8 行文字区域的触点无法到达 UIKit 层的 `PaintGestureRecognizer`。
- **修法**：`ParchmentCardModifier` 加 `backgroundHitTesting: Bool = true` 参数；HighlightBar 传 `backgroundHitTesting: false`，背景 `.allowsHitTesting(false)` 穿透给下层 FlowTextView；颜色按钮 / 完成按钮作为前景元素不受影响，仍可点击。
- **日期**：2026-09-13

## iOS 26 视觉重做：Paper = Scripture，Glass = Interface（2026-09-15）
- **决定**：iOS 原生端走「Direction 1 Glass as Instrument 主架构 + Direction 2 的羊皮材质处理」。铁律一条：**玻璃只属于操作，不属于内容**——读的时候看到的是纸，操作的时候触碰的是玻璃。
- **羊皮卷底纹保留**（Josh 2026-09-15 明确要求）：`parchment.jpg` 整图铺底的做法不动，只在它上面加极轻的边缘晕暗与暖调不均，让它从「UI 皮肤」升级成真材质；**不给羊皮页面加玻璃、不用玻璃替掉纸**。玻璃控件浮在纸之上，纸从控件后面连续延伸过去，不出现硬切边。
- **首页金句废掉双层黑色投影**：改成极轻的局部暗化（渐变遮罩），金句仍属于场景，不做成玻璃卡片。
- **底栏 + 读经坞合成一块浮起的玻璃**：不再是「两个各自画的矩形 + 6pt 缝 + 透明底栏」。
- **兼容**：一套设计两套 renderer。新增语义组件层（`AskGlass` 系列），页面里不直接写 `.glassEffect`；iOS 26+ 走 `glassEffect` / `GlassEffectContainer`，iOS 17–25 走 `.ultraThinMaterial` + hairline 描边，尺寸圆角层级交互完全一致。deployment target 保持 17.0，不抬。
- **为什么**：现有层次感 100% 靠 drop shadow + 描边硬造，视频背景上白字阴影发脏、透明底栏没有自己的视觉层；而全原生（Direction 3）会让羊皮 + 琥珀 + 自然场景这套已成形的品牌资产消失。分工清楚比"给羊皮加点玻璃"高级。

## 玻璃不着色，要系统原样渲染（2026-09-16）
- **决定**：`AskGlassSurface` 在 iOS 26 上**不再给玻璃加 tint**。照片 / 视频上用 `Glass.clear`（更透，能看见背景在玻璃里折射），羊皮纸上用 `Glass.regular`（纸对比低，需要系统那层自适应提亮把控件托起来）。玻璃上白图标的可读性改由图标自己那层极轻阴影 `askGlassIconShadow()` 负责。

## 玻璃看不出效果的真正原因：滚动视图被坞挤小，内容被裁在坞上缘（2026-09-16）
- **根因**：坞原来用 `safeAreaInset(edge: .bottom)` 挂。safeAreaInset 会**压小滚动视图的可见范围**，经文被裁在坞的上边缘 —— 玻璃底下永远只有一片空白纸。真玻璃盖在平色上跟一块底色没有区别，所以前面几轮怎么调材质都没用（Josh 连问三轮「不是玻璃，是一个底色」）。
- **修法**：坞改成 `overlay(alignment: .bottom)` 浮在内容之上；滚动长度改由 **content margin** 保证（`shellBottomInset` 现在是 `contentMargins(.bottom, glassDockHeight, for: .scrollContent)`）。content margin 只加长内容、不压小滚动视图，于是经文照常从坞底下穿过去，玻璃里能看到文字被压扁弯折 —— 效果图那个质感。
- **同时关掉系统底缘渐进模糊**（`scrollEdgeEffectHidden(true, for: .bottom)`，封装成 `askNoScrollEdgeBlur()`）：系统默认在内容贴底栏时糊一层，经文先被系统糊掉，玻璃再去折射一片糊掉的东西，两层模糊叠起来也是平的。
- **触控目标回到 ≥44**：上一轮照效果图把点击框也缩了（30–38），Josh 真机反馈「图标都比较小，会误点」。**图标小是设计，触控小是 bug** —— 视觉尺寸按效果图，点击框一律 44+。
- **一般规律**：判断玻璃效果，先确认「玻璃背后确实有内容在动」。检查顺序：① 辅助功能「降低透明度」是否开着（App 的抽屉底部会报）② 内容是否被 safeAreaInset 裁掉 ③ 系统 scroll edge effect 是否把内容糊掉了 ④ 最后才是材质档位（`.clear` / `.regular`）。
- **日期**：2026-09-16

## 2026-09-19 · 会员同步 flushNow 不能写成递归（真机启动几秒必被杀的根因）

- **决定了什么**：`MemberReadingSyncEngine.flushNow` 在 iOS / 安卓两端一律改成
  **循环 + 等完就地清 `inFlight`**，不再递归自调。
- **症状**：真机上 App 启动几秒就消失，**没有任何崩溃报告**。手机的
  `JetsamEvent-2026-09-19-145648.ips` 里记着 AskBible 连被杀三次，
  `reason = per-process-limit`，每次 `rpages = 134272`（= 2098 MB，撞穿 iPhone 12 的
  单进程上限），`cpuTime` 只有 6.3～6.8 秒。
- **根因**：`flushNow` 里「已有同步在跑就等它完再跑一轮」写成了递归：
  ```swift
  if let t = inFlight { pendingFlushReason = reason; let o = await t.value
      guard let again = pendingFlushReason else { return o }
      pendingFlushReason = nil; return await flushNow(reason: again) }   // ← 递归
  ```
  `inFlight` 的清理挂在 `schedule()` 里**另一条** Task/协程上，所以 `await t.value`
  返回时 `inFlight` 往往还指着那个**已经跑完**的 task。递归回来又 await 一个完成态
  task —— 立即返回、不让出任何时间，`pendingFlushReason` 还是自己刚写进去的，
  于是无限递归。它把 MainActor 占死，负责清 `inFlight` 的那条 Task 永远排不上队，
  循环再也出不来。
- **为什么只有登录用户中招**：入口第一行就是 `guard loggedIn`。空模拟器不复现，
  把真机的 `Library/Preferences/me.askbible.plist`（含 sessionToken）灌进模拟器后必现。
- **实测数据**：修复前峰值 **16313 MB**（4 秒破 2 GB，真机就是在这儿被杀）；
  修复后同样条件峰值 **323 MB**，40 秒平稳。`heap` 显示 820 万个 "Task stack" 占 8.4 GB，
  `malloc_history -callTree -invert` 把 5.27 GB 直接指到 `MemberReadingSyncEngine.swift:328`。
- **网页 / RN 端不用改**：它们靠 Promise `.finally()` 的时序 —— 清 `syncInFlight = null`
  发生在 `await` 返回**之前**，不存在这个窗口。这是三端对等写里少见的「写法不同反而救了一端」。
- **留下的规矩**：`inFlight` 这类「谁在跑」的句柄，**清理必须和等待在同一条执行流里**。
  只要清理另起 Task，等待方就必须在 await 之后自己再判一次、就地清掉，绝不能凭
  「它应该已经被清了」继续往下走。

## 2026-09-20 · 成就反馈 v2：声音分层，章完成升为核心事件

**背景**：v1（前一天）三个事件都有声音、都偏「奖励音」。这轮和 ChatGPT 对过一轮，
它的判断和我自己的怀疑一致：**「钟」的存在感略重，三个事件都靠钟来定义是错的**。

**定下来的反馈哲学**（这条是纲，后面所有取舍都从它推）：

> **小事靠触感，完成靠声音，成就靠钟声，升级靠光。**

**决定了什么**

1. **音色分三层**：木叩（小事）→ 小钵（完成）→ 钟（成就 / 升级）。越重要余韵越长。
   - `xp` 木叩：噪声激励 + 520/880/1450Hz 共振，70ms。原来是 1760+2637Hz 正弦，
     太电子 —— 高频正弦连响几十次非常累耳。
   - `chapter` 小钵（**新增**）：330Hz，0.55s。比木叩有余韵、比勋章钟收得快。
   - `earn` 单钟 440Hz 1.1s / `levelup` 三声上行钟 440–554–659Hz 1.9s，
     间隔 130ms（GPT 建议 100–140ms），最后一声 release 最长。
   - 钟和钵都卷了一个很短的合成混响（指数衰减噪声 IR，wet 14–22%）。
     **干声合成的钟「太近」，听着像合成器 —— 这是廉价合成音最大的破绽。**
2. **+XP 小额不出声，只给触感**；只有整章完成才出声，而且**用小钵不用木叩**
   （木叩配不上「读完一章」这件事）。
   理由：几十秒响一次，长期一定变成「游戏化噪声」；把声音留给有意义的完成节点，
   声音本身才珍贵。
3. **木叩音量 0.45 → 0.34**（GPT 建议 0.30–0.35）。
4. **升级不加全屏粒子 / confetti / 闪白**。保留「金边呼吸 + 金光扫过 + 三声钟」，
   把高级感做在时间、衰减、克制上，而不是加元素。粒子会直接把视觉语义拉向游戏产品。
   - 金光扫：1.1s → **0.62s**，峰值白 0.55 → **0.22**（GPT：500–700ms / 15–25%）
   - 金边呼吸：0.75s → **1.35s**（GPT：1.2–1.5s）
5. **网页尊重 `prefers-reduced-motion`**：开了「减弱动态效果」就不跑弹入 / 光扫 / 呼吸。
   声音不受这个偏好影响 —— 那是两种不同的偏好，别混。
6. **高亮 / 收藏保持无声**（现状就是只有触感），确认不加。高频操作出声会污染阅读环境。

**为什么记这条**：下一个来加游戏化功能的人，最容易犯的错是「给每个系统事件都配一个奖励音」。
上面那句纲领就是用来挡这件事的。

排查方法留着：**别靠眼睛判断色差，把截图的像素采出来比**。
灰调 vs 暖调（B 通道差多少）是区分「系统材质」和「我们的纸」的关键。

## 首页三颗常用键往下坠：第二个来源是安全区本身在缩（2026-09-23）

2026-09-21 修过一次（底部 padding 从 `chromeVisible ? 92 : 36` 改成写死 92），
Josh 2026-09-23 又说「隐藏其它图标时它会落到更底的位置」。

**真正的第二个来源**：界面收起时 `AskBibleApp` 把 `showTabBar` 置 false
（`!(tab == .home && homeChromeHidden)`），系统底栏被隐藏 →
`geo.safeAreaInsets.bottom` 从「底栏高 + home 指示条」缩成「只剩 home 指示条」→

改法：`lockedBottomInset` 只取见过的最大值，之后再也不跟着缩。
**以后这一排的底部间距不要再直接读 `geo.safeAreaInsets.bottom`。**

⚠️ **这条是按机制推的，模拟器上复现不出来**（两种状态量下来图标都在像素行 1633，
没动）。真机确认前别当成已验证。

## 读经坞的底改成「对齐的羊皮纸」（2026-09-23）

Josh：「圣经页的播放栏还不是羊皮卷的」。坞此前铺的是 `theme.scriptureBackground`，
那是**纯色 canvas**；而页面是**带纸纹**的羊皮底 —— 纯色贴在纸上就是一块板。

**不能直接塞一个 `ParchmentBackground`**：那张纸纹是按整屏 stretch 铺的，
塞进只有百来点高的坞里会把整张纹理压扁，和坞上方的纹理接不上，接缝一眼看得出来。

做法（`alignedParchment(theme:)`）：把纸纹按**整屏高度**画出来再往上偏移
`-(整屏高 − 坞高)`，坞露出的正好是这张纸最底下那一条，和页面是同一张图的同一段，接缝消失。
坞是贴着屏幕底的（dockFlush），所以偏移量就是这个差值。

**以后凡是要在羊皮页上铺一块不透明底的浮层，都走这条路，别用纯色。**


## alignedParchment 的两个坑（2026-09-23，当天就踩了）

第一版 `alignedParchment` 出了两个问题，Josh 一眼看出来：

1. **「上面圣经内容不见了」** —— `.background` 的内容**不会自动裁到宿主的框里**。
   整屏高的纸纹从坞里溢出去，往上把整页经文盖掉了。**必须补 `.clipped()`。**
2. **「下面变成两部分」** —— 偏移量原先按「整屏高 − 坞高」算，
   但坞下面还压着系统底栏，**它的底边并不是屏幕底边**，所以纸纹错开一截，
   坞和底栏下面那条成了两段。改成按 `g.frame(in: .global).origin` 反向偏移，
   坞在屏幕哪个位置就取纸的哪一段，和位置无关。

这两条以后做任何「对齐的底图」都适用。

## NIV 等译本改走官方 API，抓页降为兜底（2026-09-23）

Josh：「AskBible 也是做 APP 的呀，所以要优化过来」。

**原来是什么样**：`lib/bible/providers/youversion.ts` 的 `loadYouVersionChapterRows()`
**先抓 bible.com 页面，失败才回退到官方 Platform API**。于是**有授权的译本也在抓网页**。

**当初那么写不是疏忽**，是网页端的合理取舍——两个文件同一天（2026-07-15）一起加的：

| | 抓 bible.com 页面 | 官方 Platform API |
|---|---|---|
| 取一章逐节正文 | **1 个请求** | **N 个请求**（一节一个） |
| 节号哪来 | 页面里有 `data-usfm="JHN.3.1"` | 整章接口不给节号，只能逐节取 |
| 诗篇 119（176 节） | 1 个请求 | 176 个请求 |

网页端点开一章要当场渲染，抓页快好几秒。**但我们也有 App 端**
（`app/api/mobile/bible/youversion/chapter/route.ts` 走的是同一个函数），
而且加上并发和缓存之后，这个差距就没有了。

**改成什么样**：

1. **官方 API 优先**，仅对**确认有授权**的版本号（见下）。
2. **并发取节**：`VERSE_FETCH_CONCURRENCY = 10`。原来那条 API 路径是
   `for` 循环里 `await`，**串行**取 176 节——慢到根本不会有人等它。
3. **章级缓存**：进程内 Map，TTL 24 小时、上限 500 章、LRU 淘汰，不落盘。
   同一章第二次打开直接命中。
4. 抓页降为**不在授权目录的译本**才走的路。

**实测（2026-09-23）**：

| 用例 | 结果 |
|---|---|
| NIV 约翰福音 3 章 | 36 节，节号 1–36 连续 |
| 当代译本 约翰福音 3 章 | 正常 |
| 罗马书 8 章 缓存 | 首次 1031ms → **命中 0ms** |
| `lib/bible` 既有测试 | 9 个文件 37 项全过 |

### `YVP_APP_KEY` 到底授权了哪些版本

用官方目录接口拉的实际清单，**并逐个用 `passages/JHN.3.16` 验证过**
（在表里的返回正文，不在表里的一律 404）：

```bash
curl -s -H "X-YVP-App-Key: $YVP_APP_KEY" \
  --get --data-urlencode "language_ranges[]=eng" \

```

### 补漏：原生 App 的取经路由绕过了那张替换表（2026-09-23 同日）
